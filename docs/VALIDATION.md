## 1. Overview

```
generate()  ──►  [hash dedup gate]  ──►  validate_example()  ──►  Parquet shard
                       │                        │
                 duplicate_count++        rejection_reasons[err]++
```

Validation is the **last defence** before data is persisted. It runs inline inside `main_pipeline.py`'s `process_split()` function for every candidate group that survives the prior hash-based deduplication gate.

Key design principles:

- **Completeness**: all ten checks always run, even after an earlier check fails. This gives a complete diagnostic report per rejected group rather than stopping at the first error.
- **Non-destructive**: `validate_example()` never modifies the group it receives. See [§3](#3-non-destructive-contract).
- **Human-readable errors**: every check produces plain English error strings that are tallied in `stats["rejection_reasons"]` and written to `VALIDATION_REPORT.md`.

## 2. The Ten Validation Checks

### Check 1 — Proposition Count Range

**Purpose**: Ensure the group has a sensible number of propositions for non-`three_way` tasks.

**Rule**: `2 ≤ group.num_propositions ≤ 40` for all task types **except** `three_way`.

**Code** ([validators.py L93–94](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L93-L94)):
```python
if not (2 <= group.num_propositions <= 40) and group.task_type != "three_way":
    errors.append(f"Proposition count {group.num_propositions} out of range [2, 40]")
```

**Rationale**: A group with fewer than 2 propositions provides no discrimination signal. More than 40 indicates a generator bug (e.g., an unbounded loop over scene-graph edges).

`three_way` groups are **exempt** from this range check because they are handled exclusively by Check 2.

---

### Check 2 — Three-Way Exact Count

**Purpose**: Enforce the fixed-arity contract for three-way questions.

**Rule**: When `group.task_type == "three_way"`, `group.num_propositions` must equal exactly `3`.

**Code** ([validators.py L100–101](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L100-L101)):
```python
if group.task_type == "three_way" and group.num_propositions != 3:
    errors.append(f"Task type three_way must have exactly 3 propositions, found {group.num_propositions}")
```

**Rationale**: Every three-way group must have exactly one affirmative option, one negative option, and one "Cannot say" option. More or fewer would violate the evaluation protocol.

---

### Check 3 — Label Cardinality

**Purpose**: Ensure that discriminative task types have exactly one correct answer.

**Rule**: For `task_type` in `{"binary", "single_choice", "three_way"}`, `sum(labels) == 1`.

**Code** ([validators.py L108–111](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L108-L111)):
```python
labels = [p.label for p in group.propositions if p.label is not None]
if group.task_type in ["binary", "single_choice", "three_way"]:
    if sum(labels) != 1:
        errors.append(f"Task type {group.task_type} must have exactly 1 correct proposition, found {sum(labels)}")
```

**Rationale**: `multi_label` tasks are explicitly excluded — they may have any number of correct propositions from 0 to k. NONE-labeled propositions (`label=None`) are excluded from the sum via the `if p.label is not None` guard.

**Failure scenarios**:
| `sum(labels)` | Likely cause |
|---|---|
| `0` | All propositions were generated as FALSE negatives; no correct answer exists |
| `2+` | Generator produced two competing TRUE+ positive polarity propositions |

### Check 4 — Query-Template Compatibility

**Purpose**: Ensure the `query_template_id` prefix is consistent with the reasoning type and task type of the group.

**Rule**: The prefix of `query_template_id` must match the expected family for the combination of `reasoning.type`/`reasoning.family` and `task_type`:

| Reasoning family / type | Task type | Required prefix |
|---|---|---|
| `object_existence` | `binary` or `three_way` | `obj_v` |
| `object_existence` | `single_choice` | `obj_s` |
| `object_existence` | `multi_label` | `obj_m` |
| `spatial`, `contact`, `attention` | `binary` or `three_way` | `rel_v` |
| `temporal` | any | `temp` |
| `grounding` | `single_choice` | `grnd_s` |
| `grounding` | `binary` or `three_way` | `grnd_v` |

**Code** ([validators.py L120–147](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L120-L147)):
```python
if group.query_template_id:
    tid = group.query_template_id

    if group.reasoning.type == "object_existence":
        if group.task_type in ["binary", "three_way"] and not tid.startswith("obj_v"):
            errors.append("Binary object proposition must use an existence/verification query")
        elif group.task_type == "single_choice" and not tid.startswith("obj_s"):
            errors.append("Single-choice object task must use a single-object selection query")
        elif group.task_type == "multi_label" and not tid.startswith("obj_m"):
            errors.append("Multi-label object task must use a selection/set query")

    elif group.reasoning.family in ["spatial", "contact", "attention"]:
        if group.task_type in ["binary", "three_way"] and not tid.startswith("rel_v"):
            errors.append("Binary relation proposition must use a relation verification query")

    elif group.reasoning.family == "temporal" and not tid.startswith("temp"):
        errors.append("Temporal proposition must use a temporal query")

    elif group.reasoning.family == "grounding":
        if group.task_type == "single_choice" and not tid.startswith("grnd_s"):
            errors.append("Single-choice grounding task must use a region/object identification query")
        elif group.task_type in ["binary", "three_way"] and not tid.startswith("grnd_v"):
            errors.append("Binary grounding task must use verification query")
```

**Rationale**: Template IDs encode the expected evaluation format. A mismatch (e.g., an object-selection query presented alongside a temporal proposition) would produce semantically meaningless questions.

Groups with `query_template_id=None` skip this check entirely.

### Check 5 — Semantic Contradiction Detection

**Purpose**: Detect two propositions within the same group that assign contradictory truth values to the **same underlying fact**.

**How it works**:

Every proposition (except `logical_none` and UNKNOWN) is reduced to a **canonical semantic signature** — a tuple that uniquely identifies the underlying fact:

- Standard propositions: `(canonical_type, subject, predicate, object)`
- Temporal propositions: `(canonical_type, event_a, temporal_relation, event_b)`

Each signature is placed in one of two sets:

| Set | Condition |
|---|---|
| `positive_semantics` | `truth_state=="TRUE" AND polarity=="positive"` **or** `truth_state=="FALSE" AND polarity=="negative"` (double negation = assertion) |
| `negative_semantics` | `truth_state=="FALSE" AND polarity=="positive"` **or** `truth_state=="TRUE" AND polarity=="negative"` |

If the same signature appears in **both** sets, the group contains a contradiction.

**Special case — `compositional_and`**: the predicate is split on `" and "` into individual relation components. If the conjunction is TRUE, each component relation is individually added to `positive_semantics`. If FALSE, no components are added to `negative_semantics` (we cannot determine which conjunct failed).

**Code** ([validators.py L174–222](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L174-L222)):
```python
if positive_semantics.intersection(negative_semantics):
    errors.append("Contradictory labels for same semantic signature")
```

**Error string**: `"Contradictory labels for same semantic signature"`

### Check 6 — Mutual Exclusivity Detection

**Purpose**: Catch relation pairs that are **logically impossible to hold simultaneously** for the same subject–object pair.

**Table of mutually exclusive relation pairs** (defined in `MUTUALLY_EXCLUSIVE_RELATIONS`):

| Relation | Excludes |
|---|---|
| `"looking at"` | `"not looking at"` |
| `"not looking at"` | `"looking at"` |
| `"above"` | `"beneath"` |
| `"beneath"` | `"above"` |

**Rule**: For every positively-asserted `relation`-type signature `(relation, subj, pred, obj)` in `positive_semantics`, check whether any excluded relation for the same `(subj, obj)` pair is also in `positive_semantics`.

**Code** ([validators.py L236–241](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L236-L241)):
```python
if sig[0] == "relation":
    pred = sig[2]
    if pred in MUTUALLY_EXCLUSIVE_RELATIONS:
        for excl in MUTUALLY_EXCLUSIVE_RELATIONS[pred]:
            if ("relation", sig[1], excl, sig[3]) in positive_semantics:
                errors.append(f"Mutually exclusive relations {pred} and {excl} simultaneously true")
```

**Error string**: `"Mutually exclusive relations {pred} and {excl} simultaneously true"`

> [!TIP]
> To add new mutually exclusive pairs, simply extend the `MUTUALLY_EXCLUSIVE_RELATIONS` dict at the top of `validators.py`. No other code needs to change.

### Check 7 — Temporal Consistency

**Purpose**: Detect cyclic or directly contradictory temporal orderings.

**Rules** (applied to all positively-asserted temporal signatures):

| Condition detected | Error string |
|---|---|
| `A before B` **and** `A after B` both asserted | `"A before B and A after B both true"` |
| `A before B` **and** `B before A` both asserted (cycle) | `"A before B and B before A both true"` |
| `A after B` **and** `B after A` both asserted (cycle) | `"A after B and B after A both true"` |

**Code** ([validators.py L244–258](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L244-L258)):
```python
if sig[0] == "temporal":
    event_a, rel, event_b = sig[1], sig[2], sig[3]
    if rel == "before":
        if ("temporal", event_a, "after", event_b) in positive_semantics:
            errors.append("A before B and A after B both true")
        if ("temporal", event_b, "before", event_a) in positive_semantics:
            errors.append("A before B and B before A both true")
    elif rel == "after":
        if ("temporal", event_b, "after", event_a) in positive_semantics:
            errors.append("A after B and B after A both true")
```

**Rationale**: These contradictions indicate that a generator made an error when sampling temporal ordering pairs, or that the scene-graph temporal annotations are inconsistent for the sampled frames.

### Check 8 — NONE Proposition Consistency

**Purpose**: Enforce the semantic invariant for the `logical_none` "None of the above" proposition.

**Rules**:

| Scenario | Invariant | Error if violated |
|---|---|---|
| `NONE.label == 1` | All other `label` values must be `0` | `"NONE proposition is correct, but other propositions are also correct"` |
| `NONE.label == 0` | At least one other `label` must be `1` | `"NONE proposition is incorrect, but no other propositions are correct"` |

**Code** ([validators.py L270–277](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L270-L277)):
```python
none_props = [p for p in group.propositions if p.semantics.canonical_type == "logical_none"]
if none_props:
    none_p = none_props[0]
    other_labels_sum = sum([p.label for p in group.propositions if p != none_p and p.label is not None])
    if none_p.label == 1 and other_labels_sum > 0:
        errors.append("NONE proposition is correct, but other propositions are also correct")
    elif none_p.label == 0 and other_labels_sum == 0:
        errors.append("NONE proposition is incorrect, but no other propositions are correct")
```

### Check 9 — Duplicate Text Detection

**Purpose**: Ensure all proposition texts within a group are **unique**.

**Rule**: `len(set(texts)) == len(texts)`.

**Code** ([validators.py L284–286](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py#L284-L286)):
```python
texts = [p.text for p in group.propositions]
if len(set(texts)) != len(texts):
    errors.append("Duplicate proposition texts found")
```

**Error string**: `"Duplicate proposition texts found"`

**Cause**: A generator instantiated the same template twice with the same arguments, producing two identical surface strings. This typically indicates an off-by-one error in the candidate sampling loop.

### Check 10 — Surface-Form and Grammar Checks

**Purpose**: Catch several known surface-form defects that indicate template rendering bugs or incomplete ID substitution.

Six sub-checks are applied to each proposition text:

#### 10a — Empty text

```python
if not p.text:
    errors.append("Empty proposition text")
```

Catches cases where the text renderer returned `None`, `""`, or a falsy value.

#### 10b — Unresolved ID

```python
unresolved_pattern = re.compile(r'\b[orvc]\d{2,}\b', re.IGNORECASE)
if unresolved_pattern.search(p.text):
    errors.append("Unresolved ID in text")
```

Regex: `\b[orvc]\d{2,}\b` — matches tokens of the form `o12`, `r4`, `v07`, `c03`, etc. (one letter followed by 2+ digits). These are raw Action Genome object/relation/verb/class IDs that were not substituted with their human-readable labels (e.g., `"o8"` should have been resolved to `"chair"`).

**Error string**: `"Unresolved ID in text"`

#### 10c — Known bad-grammar pattern

```python
if "have it on the back" in p.text:
    errors.append("Bad grammar: have it on the back")
```

The phrase `"have it on the back"` is a specific known defect from an improperly pluralised template for the `r14` (`"have it on the back"`) relation. When the proposition renderer applies this relation in a third-person singular context, the surface form becomes ungrammatical.

**Error string**: `"Bad grammar: have it on the back"`

#### 10d — Uncountable article

```python
if "A food" in p.text or "A clothes" in p.text or "A water" in p.text \
        or "A medicine" in p.text or "A paper" in p.text:
    errors.append("Bad grammar: uncountable article")
```

Mass / uncountable nouns (`food`, `clothes`, `water`, `medicine`, `paper`) cannot take the indefinite article `"A"`. These are caught because they are the most frequent uncountable nouns in the Action Genome object vocabulary.

**Error string**: `"Bad grammar: uncountable article"`

#### 10e — Generic filler phrase

```python
if "doing something else entirely" in p.text:
    errors.append("Generic filler negative used")
```

The phrase `"doing something else entirely"` is a lazy placeholder sometimes produced by negative-proposition templates that cannot find a specific distractor action. Such propositions lack the semantic specificity required for meaningful evaluation.

**Error string**: `"Generic filler negative used"`

#### 10f — Double negation

```python
if "not not" in p.text.lower():
    errors.append("Double negation")
```

The string `"not not"` (case-insensitive) appears when two negation templates are composed without detecting that the inner template was already negative, producing a logically positive claim in negative syntactic clothing.

**Error string**: `"Double negation"`

## 3. Non-Destructive Contract

`validate_example()` has a strict **read-only** contract:

```python
def validate_example(group: PropositionGroup) -> Tuple[bool, List[str]]:
```

- The function **never modifies** `group`, its `propositions`, or any nested `semantics` / `provenance` object.
- It only reads field values and accumulates error strings.
- The caller retains full ownership of the group object.

This means that if a group fails validation, the calling code can safely log or inspect the group without risk of observing a half-modified state. It also means validation can be called in parallel across multiple groups without locking.

**Return value**:

| Element | Type | Description |
|---|---|---|
| `[0]` | `bool` | `True` if **all** checks passed (errors list is empty); `False` otherwise |
| `[1]` | `List[str]` | Possibly-empty list of human-readable error strings (one per violated check) |

**Example usage**:
```python
from src.validation.validators import validate_example

ok, errors = validate_example(group)
if not ok:
    for err in errors:
        logging.warning("Rejected group %s: %s", group.example_id, err)
```

## 4. Rejection Tracking

`main_pipeline.py` tracks rejections at two granularities using `collections.Counter` objects inside the `stats` dictionary:

### Per-generator rejection counts

```python
stats["rejected"][gen_name] += 1    # incremented once per rejected group
stats["accepted"][gen_name] += 1    # incremented once per accepted group
stats["candidates"][gen_name] += 1  # incremented for every candidate before any filtering
```

These counters let you assess which generator is the noisiest — i.e., which one produces the most candidates that fail validation.

### Per-error-string rejection reasons

```python
is_valid, errors = validate_example(group)
if not is_valid:
    stats["rejected"][gen_name] += 1
    for err in errors:
        stats["rejection_reasons"][err] += 1
```

Because `validate_example()` never short-circuits, a single rejected group may contribute **multiple** entries to `rejection_reasons` (one per violated check). The `rejection_reasons` counter therefore counts **violations**, not groups.

### Reported in VALIDATION_REPORT.md

After generation completes, `main_pipeline.py` writes `VALIDATION_REPORT.md` which includes:

| Metric | Description |
|---|---|
| **Total candidates** | Raw groups produced by all generators before any filtering |
| **Duplicates discarded** | Groups that matched a hash already in `seen_hashes` |
| **Validation rejections** | Groups that failed at least one `validate_example()` check |
| **Accepted** | Groups written to Parquet shards |
| **Rejection reason breakdown** | Top rejection error strings and their frequency counts |

## 5. Adding a New Check

To extend `validate_example()` with a new validation rule, follow these steps:

**Step 1**: Open [`src/validation/validators.py`](file:///c:/Users/GANAPATHI/Desktop/NIT/Research/UniProp/src/validation/validators.py).

**Step 2**: Locate the position where the new check logically belongs (after Check 10, or inline between existing checks if it is closely related).

**Step 3**: Write the check using the established pattern:

```python
# ------------------------------------------------------------------
# Check N: <one-line description of what is being checked>.
# <Extended rationale explaining why this check is necessary.>
# ------------------------------------------------------------------
if <condition that indicates a violation>:
    errors.append("<Human-readable error string>")
```

Rules:
- **Always append to `errors`**; never `raise` an exception or `return` early.
- **Never modify `group`** or any of its nested objects.
- Keep the error string short (< 80 chars) and specific enough to diagnose the problem from `VALIDATION_REPORT.md`.
- If the check requires a module-level constant (e.g., a lookup table like `MUTUALLY_EXCLUSIVE_RELATIONS`), add it at the top of the file with a descriptive comment.

**Step 4**: Add a corresponding test in [`tests/test_validators.py`](file:///c:/Users/GANAPATHI/Desktop\NIT\Research\UniProp\tests\test_validators.py) that:
1. Constructs a `PropositionGroup` that **violates** the new rule and asserts `ok == False` and the expected error string is in `errors`.
2. Constructs a `PropositionGroup` that **passes** the new rule and asserts `ok == True`.

**Step 5**: Update the module-level docstring in `validators.py` to add the new check to the numbered list under `Checks performed (in order)`.

**Step 6**: Update this document (§2) to add a new sub-section documenting the check's purpose, rule, code snippet, and error string.

> [!TIP]
> Run the test suite with `pytest tests/test_validators.py -v` after adding the check to confirm no regressions in existing checks.
